c1 / c2 코드북 그룹 생성 방식

RQ-VAE 학습 이전 전처리(src/) 단계에서 Semantic ID의 c1, c2 그룹 기준을 만드는 방식을 정리한 문서입니다. RQ-VAE 내부(코드북 초기화, SID 생성)는 다루지 않습니다.

c1

model_category_id

원본 category_str을 train 기준으로 정수 매핑. 카테고리 1개 = 그룹 1개.

c2

event_id

Entity 기반 사건 클러스터. IDF 가중 Jaccard + 72시간 창 + Union-Find.

0. 실행 순서와 공통 원칙

src/run_article_build.py의 main()이 아래 순서로 실행합니다.

유효 기사 선별→ train 사용 기사 ID→ 카테고리 매핑 생성→ 매핑 적용→ E5 임베딩→ train 사건 생성→ train article master 
build_valid_articles()               # STEP 2  유효 기사 선별 → articles_base.parquet

이후 src/main.py에서 build_validation()(validation 사건 배정)과 export_rqvae_inputs()를 호출합니다.

공통 원칙 — c1·c2 매핑은 모두 train에서 실제 사용하는 기사만으로 만들고, validation에는 적용만 합니다.
선행 조건 — c2에서 쓰는 article_entities.parquet은 build_article_entities()가 만듭니다. 이 함수는 run_article_build에 포함되어 있지 않으므로 src/run_entity_experiment.py로 먼저 생성해야 합니다. 없으면 사건 생성 단계에서 에러가 납니다.

1. c1: 카테고리 그룹 (model_category_id)

1-1. 매핑 생성

build_category_mapping() · src/build_train.py:601

  1. train 사용 기사에 category_str 연결

  4. 정렬 순서대로 1부터 연속 ID 부여, <UNK> = 0 예약 (원본에 <UNK> 문자열이 있으면 에러)
  5. 저장: category_mapping.parquet

1-2. 전체 기사 적용

apply_category_mapping_to_articles() · src/build_train.py:805

  • 전체 유효 기사의 정리된 category_str을 기준으로 left join
  • 매칭이 안 되면 0 (빈 카테고리, train에 없던 카테고리)
  • 리포트: 빈 카테고리 기사 수, train에 없던 카테고리의 기사 수·종류 수·예시(최대 10개)
  • validation도 같은 frozen 매핑을 사용 (src/main.py:390)
카테고리 병합이나 희소 카테고리 통합은 하지 않습니다. 원본 카테고리 1개가 그대로 c1 그룹 1개입니다.

2. c2: 사건 그룹 (event_id)

2-1. Entity 표현

src/entity_processing.py

ENTITY_PROCESSING_MODE = "normalize_only"
ENTITY_NORMALIZATION_VERSION = "v2"

사건 클러스터링은 load_canonical_entity_lookup()으로 article_id → set[canonical_entity_key]를 읽어 사용합니다.

단계처리예
baselineNFKC → 공백 축약 → 소문자, TYPE::text 키PER::vladimir putin
v1 소유격끝 -s를 떼어 원형으로 병합ekstra bladets → ekstra bladet
v2 하이픈하이픈을 공백으로 바꿔 병합jyllands - posten → jyllands posten

v1 오병합 방지 조건

  • PER / ORG / LOC만 대상
  • 원형이 같은 TYPE의 train 어휘에 실제로 존재
  • 원형 길이 ≥ 3, 원형 df ≥ 2, 원형 df ≥ -s형 df
  • Andreas → Andrea, Sky Sports → Sky Sport 같은 잘못된 변환 방지

v2 오병합 방지 조건

  • 같은 TYPE 안에서만 매핑
  • 변환 결과가 같은 TYPE의 train 어휘에 존재
  • midt -처럼 시작·끝에 매달린 하이픈은 제외
  • 끝 구두점(allan j.)은 처리하지 않음

정규화 매핑은 train 사용 기사로만 만들고 전체 유효 기사에 적용합니다.

2-2. Train 사건 생성

build_article_events() · src/build_train.py:1884

파라미터환경변수기본값
유사도 임계값 θSID_EVENT_SIMILARITY_THRESHOLD0.3
시간창SID_EVENT_TIME_WINDOW_HOURS72
흔한 엔티티 제외 비율SID_EVENT_MAX_ENTITY_DF_RATIO0.01
  1. train 사용 기사를 (published_time, article_id) 순으로 정렬
  2. Entity IDF (_build_train_entity_idf)
    • idf(e) = log((N+1) / (df(e)+1)) + 1
    • train에 없던 엔티티: log(N+1) + 1
  3. 흔한 엔티티 제외: train 기사의 1% 이상에 나오는 엔티티(예: ORG::ekstra bladet)를 뺀 clustering_entity_set 생성. 원본 엔티티 집합은 보존
  4. 연결: 정렬된 기사를 순회하며 72시간 이내 쌍만 비교, 72시간을 넘으면 break 
    sim(A, B) = Σ_{e ∈ A∩B} idf(e) / Σ_{e ∈ A∪B} idf(e)    # IDF 가중 Jaccard
    • 한쪽이 비어 있거나 교집합이 없으면 0
    • sim ≥ θ이면 Union-Find로 합침
  5. 사건 확정: 연결된 기사 묶음(connected component) 1개 = 사건 1개
    • 연결되지 않은 기사(엔티티 없는 기사 포함)는 혼자 사건 하나
    • 연결이 전이되므로 A–B, B–C만 연결돼도 A·C가 같은 사건이 되고, 사건 지속 기간이 72시간을 넘을 수 있음
  6. ID 부여: 사건을 (event_start_time, first_article_id) 순으로 정렬해 0, 1, 2, …. 각 사건에 엔티티 합집합, 시작 시각, 마지막 기사 시각, 기사 수 저장
  7. 출력: article_events.parquet, event_master.parquet, entity_idf.parquet (entity, document_frequency, document_frequency_ratio, idf, is_high_df)

2-3. Validation 사건 배정

_assign_validation_events() · src/build_validation.py:370

train 사건은 다시 클러스터링하지 않습니다. validation에만 있는 기사를 (published_time, article_id) 순으로 하나씩 처리합니다.

  1. 엔티티는 같은 canonical key를 쓰고, 흔한 엔티티 목록과 IDF는 train 결과를 재사용
  2. 후보 사건: 0 ≤ 기사 시각 − 사건의 마지막 기사 시각 ≤ 72h (미래 정보 차단)
  3. 후보 사건의 엔티티 합집합과 IDF 가중 Jaccard 계산
  4. sim ≥ θ인 후보 중 가장 유사한 사건에 배정 (동점이면 작은 event_id). 배정 후 사건의 엔티티 합집합, 마지막 기사 시각, 기사 수를 갱신하므로 이후 기사의 매칭에 영향을 줌
  5. 맞는 사건이 없으면 validation에서 새로 생긴 사건으로 새 ID 부여
  6. 출력: validation_article_events.parquet, event_master_with_validation.parquet (train용 event_master.parquet은 덮어쓰지 않음), validation_article_master.parquet

2-4. Entity Linking 실험 변형

event_entity_linking/

엔티티 표현만 GPT/Wikidata entity linking 결과(article_linked_entities.parquet)로 바꾸고, 같은 사건 정책(0.3 / 72h / 0.01)으로 사건을 다시 만드는 실험용 패키지입니다. 자세한 내용은 event_entity_linking/README.md를 참고하세요.

3. RQ-VAE 전달 형태

build_train_article_master() / build_validation_article_master() → export_rqvae_inputs()가 필수 컬럼과 ID 중복·null 여부를 검사한 뒤 내보냅니다.

article_id | embedding_row | model_category_id (c1) | event_id (c2)

4. 확인이 필요한 점

  1. 연결의 전이성: 직접 비교하지 않은 기사도 같은 사건이 되므로 큰 사건 하나가 비정상적으로 커질 수 있습니다. 사건 크기 분포를 확인할 필요가 있습니다.
  2. train과 validation의 방식 차이: train은 기사끼리 연결하고, validation은 기사를 사건의 엔티티 합집합과 비교해 가장 가까운 하나에 붙입니다. 사건의 엔티티 합집합이 커질수록 Jaccard 분모가 커져, 큰 사건에는 새 기사가 붙기 어려워질 수 있습니다.
  3. 엔티티가 없는 기사는 모두 혼자 사건 하나가 됩니다. 1개짜리 사건 비율을 리포트로 확인하는 것이 좋습니다.
  4. 카테고리를 원본 그대로 사용: 희소 카테고리 병합이 없습니다. RQ-VAE의 vae_num_categories(현재 gin 설정 25)가 max(model_category_id) + 1 이상인지 확인해야 합니다.
